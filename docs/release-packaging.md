# ALAS release packaging

`cargo xtask dist` builds the release binary and assembles a portable package under `dist/`. The package directory name is derived from the `xtask` Cargo package version and the compilation target, for example `alas-v1.2.0-windows-x86_64` or `alas-v1.2.0-linux-x86_64`. v1.1.0 was the first native Rust release; the historical Python project's `1.0.0` label was not inherited. ALAS 1.2 continues the same native-Rust versioning. The archive format follows the target: `.zip` on Windows, `.tar.gz` everywhere else (`xtask/src/dist_archive.rs`), because a zip does not reliably round-trip a Unix executable bit and `tar` is the format already present on every mainstream Linux distribution and macOS.

Every package contains `RELEASE-MANIFEST.json`. It records the version, target, release channel, source commit, dirty-worktree flag, statuses of adjacent solvers, and SHA-256/byte counts for each packaged artifact. `external_tools` names every solver the application can call: `avl` and `nastran95` carry the actual bundle outcome for this package, and `mses`, `vspaero`, `msc_nastran`, `msc_patran` and `flowunsteady` are recorded `"user_supplied"` because their licences or user-selected external releases make them this task's permanent non-bundling decision, not an incomplete-staging result. Each entry's reason points to `THIRD-PARTY-NOTICES.md` for the exact licence. `SOURCE-MANIFEST.json` records the corresponding ALAS source files and their hashes. The source snapshot is assembled by the positive allowlist in `xtask/src/dist.rs`: Rust source and crate manifests, the explicitly named compile-time data and test-fixture directories, the exact golden fixtures required by current `include_str!`/`include_bytes!` consumers, one individually reviewed `golden/` evidence file the shipped real-aircraft parity harness needs at runtime (`allowed_reviewed_evidence_files` in `SOURCE-MANIFEST.json` — see below), allowlisted utility scripts under `tools/`, approved text/data files under `docs/` and `.cargo/`, and the root manifests plus compile-time branding/texture assets. The manifest records each of these allowlist categories so a reviewer can inspect the selection. It excludes proprietary `external tools/`, `.agent/` evidence, generated output directories, golden/parity data outside the eight named compile-time fixtures and the one reviewed evidence file, PDFs, images outside the named assets, the unused `assets/textures/natural_earth_110m_land.geojson`, and common secret-bearing names. `.gitattributes` travels with the snapshot so the `-text` rule protecting the byte-exact UIUC Selig corpus survives extraction on hosts with line-ending conversion. A dirty-worktree flag is retained in the manifest so a package built before a release commit cannot be mistaken for a reproducible tagged release.

AVL 3.52 travels as an adjacent GPL child executable only on the Windows package, where the only AVL build this task has reviewed and tested (the official win32 executable already staged in `external tools/`) actually runs; that package's own distribution validation run exercises it and requires its total-force output and the `Athena AVL` Model Comparison overlay. Every other package (`xtask/src/dist_avl.rs`) ships the same GPL corresponding source archive and licence text plus a written `external tools/AVL-LINUX-BUILD.txt` note pointing at the archive's own `gfortran` build targets (`bin/Makefile.gfortranDP`, `plotlib/config.make.gfortranDP`, `eispack/Makefile.gfortran`), and records `external_tools.avl.status = "not_bundled"` with that reason; its validation run instead confirms the packaged binary completes a headless analysis through ALAS's own analytical vortex-lattice stage with no AVL configured. This task does not attempt to build AVL from that Fortran source unattended in CI: doing so would be a separate, unverified engineering step, and shipping the Windows executable inside a non-Windows package would be worse than shipping neither — it would not run there. NASTRAN-95 is optional in the default mode on every target. When the local staging tree is missing or its provenance is incomplete, the task omits it and records `external_tools.nastran95.status = "not_bundled"` with the specific reason; no placeholder directory or executable is created. This is the expected result on a checkout without NASTRAN-95 staging. `assess_nastran95`'s required-file list is itself still Windows-only (`build/bin/nastran.exe`); that is unreviewed for this release and remains a known limitation for a future reviewed Linux NASTRAN-95 bundle, not something the default (unbundled) mode depends on.

The MSES release resource is recorded separately as `bundled_resources.mses_osmap`.
The compatible GPL double-precision map, exact XFOIL source archive, GPL text,
provenance README and acquisition script are copied under `assets/mses/`;
the MSES executables remain user-supplied.

The release guard hashes the bundled `osmapDP.dat` and exact XFOIL 6.99
archive, checks the GPL provenance files, and verifies the double-precision
Fortran record header before it writes the archive. At runtime, ALAS resolves
the map from the explicit configuration, `MSES_OSMAP`, the selected MSES
directory, or the package's own `assets/mses/` path. The selected absolute
path is passed to the MSES child process through `MSES_OSMAP`, so launching
the packaged application from another working directory does not make a valid
free-transition run appear to have a missing database.

An intentional bundled NASTRAN-95 package must opt into the fail-closed check:

```powershell
$env:ALAS_STRICT_BUNDLED_NASTRAN95 = "1"
cargo xtask dist
```

Strict staging requires the executable, rigid formats, NOSA license text, modification record, source archive, a `runtime/` directory, and `runtime/DEPENDENCIES.txt`. The dependency inventory must list each runtime DLL exactly once by basename, every listed DLL must exist, and every DLL present in that directory must be listed. `SOURCE-REVISION.txt` must contain no statement disclaiming reproducible executable/source association and must declare a 64-digit SHA-256 matching the staged source archive. The strict mode fails before creating an archive if any of these checks fail. Runtime execution is still a separate engineering qualification step; packaging metadata does not certify NASTRAN performance.

Validation runs the packaged binary with `--help`, exports and reads a configuration file, and writes a headless run under a temporary directory whose path contains spaces. Where AVL is actually bundled (the Windows package) it additionally checks that AVL total-force files and the `Athena AVL` model-comparison overlay are present; where it is not (every other package), it instead confirms the same headless run still completes and still produces the Model Comparison figure through ALAS's own analytical fallback. The generated archive is created only after these checks pass; a sibling `.zip.sha256` (Windows) or `.tar.gz.sha256` (elsewhere) file records its SHA-256. Use `ALAS_STRICT_BUNDLED_NASTRAN95=1` only when the source/binary/runtime association and redistribution records have been reviewed for the exact staged build.

## Three distinct things that are all "a package"

These are not interchangeable, and nothing here promotes one into another automatically:

- **A produced local package.** Whatever `cargo xtask dist` writes to `dist/` on a developer's own checkout. It carries that checkout's dirty-worktree flag and whatever `external tools/` staging happened to be present locally. It never leaves that machine unless someone copies it.
- **A CI workflow artifact.** `.github/workflows/release-preflight.yml` (Windows only) and `.github/workflows/release-package.yml` (Windows and Linux; below) each run `cargo xtask dist` on a clean GitHub Actions checkout and upload the resulting archive, its checksum, `RELEASE-MANIFEST.json`, `SOURCE-MANIFEST.json`, and a recorded toolchain/target file as a workflow-run artifact. That artifact is reproducibility evidence for reviewers with repository access; it is not published anywhere public, has no download page, and expires under the repository's normal Actions artifact retention.
- **An externally published release.** A maintainer-authored GitHub Release (or other distribution channel) that attaches a specific, reviewed, tagged package for public download, as described in `downloads.md`. Nothing in this repository's CI creates one automatically; publishing a release remains a deliberate, separate, human-gated action.

## CI release preflight

`.github/workflows/release-preflight.yml` is a manual (`workflow_dispatch`-only) GitHub Actions workflow, predating the Linux package lane below. It does not run on `push` or `pull_request`, creates no GitHub Release, pushes no tag, and publishes nothing outside its own workflow-run artifact. On `windows-latest` it checks out the repository (the `external tools/` staging this task depends on, such as AVL, is tracked in git and comes with the checkout), installs the pinned `1.97.1` toolchain from `rust-toolchain.toml`, records the exact `rustc`/`cargo`/target-triple versions to a file, runs the existing gate (`cargo xtask gate`: repository checks, formatting, clippy, and the workspace test suite) before packaging, then runs `cargo xtask dist`, which itself builds with `cargo build --release --locked`, i.e. strictly from the committed `Cargo.lock`. It uploads the resulting archive, its `.sha256`, `RELEASE-MANIFEST.json`, `SOURCE-MANIFEST.json`, and the recorded toolchain/target file as one workflow-run artifact. Its own `ubuntu-latest` job remains `cargo check --workspace --locked --all-targets` only, with no packaging step; it catches Linux compile regressions early and is otherwise superseded, for an actual package, by the workflow below.

## CI release package (Windows and Linux)

`.github/workflows/release-package.yml` is the genuine two-platform packaging workflow: a `workflow_dispatch`/`push: tags: v*` matrix over `windows-latest` and `ubuntu-22.04`. `ubuntu-22.04` (glibc 2.35), not the rolling `ubuntu-latest` label, is the deliberate older-glibc baseline so a package built there keeps running on a distribution with an equal or newer glibc; letting the label roll forward would silently raise that floor on a later run. Like `release-preflight.yml`, it creates no GitHub Release, pushes no tag, and publishes nothing beyond its own workflow-run artifacts.

Each matrix job checks out the repository, installs the pinned `1.97.1` toolchain, and — on the Linux runner only — installs the system packages `cargo xtask dist` needs to link eframe's windowing and font stack: `pkg-config`, `libwayland-dev`, `libxkbcommon-dev`, `libxkbcommon-x11-dev`, `libx11-dev`, `libxcursor-dev`, `libxrandr-dev`, `libxi-dev`, `libxext-dev`, `libgl1-mesa-dev`, `libegl1-mesa-dev`, `mesa-vulkan-drivers`, `libfontconfig1-dev`, and `xvfb`. That list was derived by reading the winit 0.30 / wgpu 22 / wayland-client / smithay-client-toolkit / font-kit dependency chain in `Cargo.lock` and cross-checked, from a Windows development host with no Linux linker, by running `cargo check --target x86_64-unknown-linux-gnu -p alas-app`: that check compiled clean through every `alas-*` engineering crate and egui's own font stack, and failed only where a genuine Linux target is unavoidable — `yeslogic-fontconfig-sys`'s `pkg-config` probe for system fontconfig, which is exactly what `libfontconfig1-dev` supplies. Whether the full list is sufficient for a real link can only be confirmed by this workflow's own first run; a missing package fails fast and visibly at `cargo xtask dist`'s build step.

Each job then runs `cargo xtask gate` (repository checks, formatting, `clippy -D warnings`, and `cargo test --workspace`, all from the locked dependency graph) before packaging, runs `cargo xtask dist`, locates the assembled package directory, runs the opt-in `crates/alas-acceptance/tests/distribution_license_boundary.rs` suite against it with `ALAS_W55_PACKAGE_DIR` set (the same suite `release-preflight.yml` never exercises, because that workflow never names a package to it), and runs a second, CI-level headless smoke of the packaged binary's `-h`/`--help` (this CLI has no `--version`) directly from the unpacked package — wrapped in `xvfb-run` on Linux, defensively, since `--help` does not construct a window today but the wrapper costs nothing once `xvfb` is installed above. It then uploads the archive, its checksum, `RELEASE-MANIFEST.json`, and `SOURCE-MANIFEST.json` as one workflow-run artifact per platform.

On the Linux package specifically, `cargo xtask dist`'s own AVL handling (`xtask/src/dist_avl.rs`, see above) means the packaging step, the license-boundary suite, and the smoke test all exercise the analytical-fallback path with no AVL executable bundled; they do not and cannot prove that a *built* Linux AVL executable, dropped in afterward by a user, integrates correctly, since this task builds none. The pre-existing `dependencies` job in `i18n-verification.yml` (cargo-deny license/advisory/source check) remains the authoritative Linux-hosted dependency check and is unchanged by either workflow.

## Test and parity-harness reproducibility from the source archive

The source snapshot gives an extracted checkout enough to run `cargo test --workspace --no-run --locked` (every test target compiles) and to fully *run* two categories of check with nothing further needed:

- The handful of test targets whose fixtures are the eight compile-time-embedded `golden/` files above (`alas-report`'s `parity_geometry_w32`, `parity_structures_w38`, `parity_optimization_w39`, `parity_screening_w39`, `parity_aerodynamics_w31`, its `mission`/`mass_balance_layout` unit tests, and `alas-uav`'s `propulsion_electric` tests and library code): those fixtures are baked into the compiled binary.
- The shipped real-aircraft comparison harness, `tools/aircraft_parity.cjs`, together with its one required input `golden/aircraft/real_aircraft_parity.json`. That file was read in full and reviewed before admission: every numeric entry is a short factual value (a dimension, mass or count) with a `cite` key into a `sources` bibliography whose 50 entries carry only `title`/`authority`/`url` — never a quoted, excerpted or reproduced passage from the cited manufacturer or regulatory document, no images, no secrets. Citing a source by title and URL is not redistributing it. This is a project-authored evidence-anchor database, not embedded third-party expressive content, so it is admitted by exact path in `SOURCE_REVIEWED_EVIDENCE_FILES` — a one-file allowance, not a `golden/aircraft` prefix rule. A source-tree copy of the file staged into `source/alas/golden/aircraft/real_aircraft_parity.json` was confirmed byte-identical to the tracked working copy and loads cleanly through `node tools/aircraft_parity.cjs --contract <staged path> --model <any model dump>`, evaluating all 7 aircraft presets and 241 checks. Running the full comparison (rather than just loading the contract) still needs a real model dump: `cargo run -p alas-pipeline --example model_reference_dump`, then `node tools/aircraft_parity.cjs` with its defaults.

The much larger historical parity suite — 88 test files across the workspace, reading roughly 85 MB under `golden/` at *runtime* through `alas_testkit::golden_dir`/`load_json`/`load` — remains a separate, still-excluded case, pending an individual provenance review of each fixture the way the real-aircraft contract above received one; it is not folded into today's admission. Those fixtures are generated output from a separate historical Python reference implementation (`golden/generators/gen_<family>.py`, 79 scripts, run against that reference codebase, not against ALAS itself); `alas_testkit::load_json`'s own panic message names the exact regeneration step: run the matching `golden/generators/gen_<family>.py` against that reference implementation, which is not part of this repository or archive. Admitting the whole `golden/` directory by a broad rule remains exactly the kind of blanket allowance this allowlist is designed to avoid. A maintainer who needs the full historical parity suite to run from an extracted archive should copy the regenerated `golden/` tree in alongside the archive's `source/alas` checkout rather than expect the archive to carry it.
